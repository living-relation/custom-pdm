# custom-pdm firmware port + host simulation: results (2026-11-10)

Nothing pushed, nothing flashed. Merged into `main` of the custom-pdm repo on 2026-11-10. Base: dingoFW `development` @ `14084e9` (2026-10-30, MIT; was master `d594cd7` until 2026-11-14), ChibiOS kept as a git-ignored local clone (`firmware/ChibiOS`, corygrant/ChibiOS @ 879cf757, the same pin in both), untouched.

## What was built
- `boards/custompdm_a` (from `dingopdm_v7`) and `boards/custompdm_b` (from `dingopdmmax_v1`), generated by `tools_custom/port_boards.py` from `docs/firmware-pin-map.md`.
- Shared-code edits: `ProfetModel::BTS7004_1EPP` (kILIS 20000, Infineon data sheet typ.), `LINE_E2` debug writes guarded, per-input wake mask in `core/sleep.cpp` (build-time until B2, a config param since 2026-11-14).
- All seven builds compile (A unit 1, A unit 2, B, 4 stock) with arm-none-eabi-gcc 13.2.1 in the cloud (upstream pins 14): 0 warnings. With 14.2.1 on DansPC WSL the linker adds one "RWX segment" warning. Flash use 31 % on both custom boards.
- `sim/`: host build of the real firmware logic (core, comms, functions, board folder) against a small ChibiOS/HAL stand-in. One shared object per board; Python runs boards, CAN bus, ECU and a PC-tool stand-in in lock step.

## What the simulation models
GPIO reset state from `board.h`; pin modes; software-PWM timers; ADC sequence registers decoded to physical pins; PROFET sense path (DEN, DSEL, kILIS, 1.2 k); input-board DIP pulls and 10k/20k divider; bxCAN (3 TX mailboxes, 3-deep RX FIFO, list filters, bit timing); CAN arbitration and ACK; FRAM contents across power cycles; ChibiOS 100 us tick rounding.
Hardware models are written from the pin map, not from the firmware port. Planted errors (swapped ADC slots, wrong DSEL pin, wrong input pin) are caught: 32 of 36.

## What it does not model
Analog settling and noise, interrupt timing, the LM2902 output limit (sense clamp assumed 3.3 V), USB (bridge is from code reading only), boot pins (BOOT1), brown-out, real CAN error frames, dingoConfig (the PC app; its param / CRC / decode paths for types 14 / 15 are covered by `ui/tests` since PR #65). APB1 = 36 MHz is taken from the `port.cpp` comment.

## Choices made (Dan's answers: `DECISIONS.md`, "Firmware and coordination")
- New status frame 37 (base + 39; was 27 until the dingoFW `development` port, which uses 27-36): 16 input bits, analog mV, analog raw, STM32 die temperature x10 signed (bytes 6-7, since 2026-11-14). `NUM_TX_MSGS` 38. Byte 0 of frame 0 now carries inputs 1-8.
- Device type in msg 0 byte 1 bits 4-7 (4 bits): 14 board A, 15 board B (stock 0 / 1). Upstream uses 0-4 and counts up; dingoConfig `development` looks a type up by its value (`FwDeviceDefManager.GetByDeviceType`), not by list position, so gaps are allowed; the 4-bit field caps types at 15.
- Wake-up set (Dan B2, built 2026-11-14): no input wakes by default (CAN and USB do); per-input "may wake" mask in param `0x7F00` sub 5, refused when it arms two inputs of one shared line or the input on the USB D- line (rules and the warning frame: `docs/firmware-pin-map.md` section 6). Replaced the build-time `WAKE_DIG_INPUT_MASK` (A 0x73, B 0x0FF). `LINE_UNUSED` = PB2 on board B, input with pull-down (Q4 in `docs/firmware-pin-map.md`).
- Factory defaults per build (Dan, C1a/C2a 2026-11-10): 1 Mbit/s; base ID 0x500 (A unit 1), 0x540 (A unit 2), 0x580 (B) since the `development` port (was 0x500 / 0x520 / 0x540: one board now uses base .. base + 0x27, 40 IDs, so 0x20 apart overlapped; 0x40 leaves 24 spare per board), example values; overcurrent reset mode Count (3 tries). Fan remote-temperature CAN inputs follow them (0x502 / 0x582, `port_boards.py`). Build with `make BOARD=custompdm_a UNIT=2`. All stay changeable over CAN/USB.
- Analog reading scaled x1.5 to volts at the wire. BTS7004 noise floor 0.5 A (not measured).
- Thermal factory defaults (2026-11-14, r5a / r7a; fan switching s12a / s13a): limits 55 / 80 / 6 C, critical-soon margin 5 C, A2 OUT2 fan output on at 45 / off at 40 C on the hottest board (1 A limit), load-shed example disabled. The S2 "one PDM" recipe still writes all 24 outputs, so it overwrites the fan output's default; S4 checks the fan on fresh boards. Stock builds unchanged (dingopdm_v7 binary byte-identical to the upstream base it is built from).
- Board B input 5 is on PC13 (B1: decided 2026-11-10, built 2026-11-11 in PR #12: board scripts, firmware and the simulation's board model changed together).

## Seen in stock firmware (not changed)
- The first round of cyclic msgs is built in InitCan (CAN TX thread, NORMALPRIO + 1), before the device thread reads any input: that round reports inputs, outputs and analog values as 0 (2026-11-16, w1). Changed for our msg 37 only.
- Stock factory default is ID 0x0DE at 500 kbit/s on every board (custom builds override it).
- With the CAN filter option on, the board stopped answering the tool over CAN on master `d594cd7` (filter slot 0 was base - 1, requests arrive on base + 1). Fixed upstream in `development` (filter list starts with base + 1); `s1` extras: tool answered with the filter on.
- Output current goes out on CAN in whole amps; the DBC file says 0.1 A per count.
- Stock default overcurrent reset mode is None: one trip latches Fault until a power cycle (custom builds default to Count).
- A second pin on the same EXTI number replaces the first as wake source (ChibiOS asserts are off).
- dingoFW `development` (code read, not tested): digital-input PWM measurement reports inputs 1-6 only (msgs 34-36; boards A / B have 7 / 10 inputs), and it uses the input's EXTI line, so two PWM inputs on one shared line (A: PA10 / PC10, PC11 / PA11 = USB D-; B: PA10 / PC10, PC11 / PA11) cannot both work. With Count reset mode the last allowed trip goes Overcurrent -> Fault in the next 2 ms cycle (no reset-time wait). Blink keypads send on node ID + 0x180 .. + 0x500 (e.g. node 0x15: 0x515 inside board A1's block); not used here.
