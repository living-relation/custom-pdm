# ui - PC configuration tool

`dingoConfig/` is upstream dingoConfig (MIT, licence in `dingoConfig/LICENSE`), copied in the same way dingoFW lives in `firmware/` (DECISIONS 2026-11-10 B2a, K1a route A). Nothing goes upstream.

- Upstream: https://github.com/corygrant/dingoConfig, branch `development`, commit `01134ad057dee5c69788ccfecf63420740e932bc` (2026-10-26, "bump version"). It matches our firmware's dingoFW `development` @ 14084e9.
- Import commit: unmodified copy (tree hash equal to upstream `e9202a9`). Our changes are separate commits on top, so `git diff <import commit> -- ui/dingoConfig` shows all of them.
- Build output (`bin/`, `obj/`) is git-ignored.

## Our changes (route A)
- Device types 14 (board A) and 15 (board B): `dingoConfig/web/Definitions/device-definitions.json` plus `custompdm-a-signals.json` / `custompdm-b-signals.json` (cyclic layout of `firmware/boards/custompdm_*/msg.cpp`).
- Param block 0x7F00 (temperature limits, critical-exempt outputs, critical-soon margin, wake inputs): `dingoConfig/domain/CustomPdm/CustomPdmSettings.cs`, hooked into `FwDevice` for types 14 / 15 only. Shown on the device Configuration tab (Device panel); die temperature and the thermal flags on the device status (Dashboard) tab. Wake inputs on a shared line / the USB line are greyed out. For types 14 / 15, Read / Write Modified are off and Write All needs a successful Read All first (a new project holds stock dingoPDM defaults, not our factory defaults; A2 could otherwise be written with A1's ID).
- Route B phase B1 (`docs/ui-route-b-plan.md`): page `/pdm` (menu entry PDM), a read-only live view of the three boards as one PDM: `dingoConfig/domain/CustomPdm/PdmView.cs` (roles, numbering, connector pins from `docs/box-connectors.md`) and `dingoConfig/web/Components/CustomPdm/PdmPage.razor`. Board roles: the two type 14 devices by base ID are A1 then A2; the type 15 device is B.
- Route B phase B2: `/pdm` is editable (outputs: enable, name, current / inrush limit, inrush time, reset mode, reset count limit, reset time; digital inputs: enable, name, mode, pull, invert, debounce; stock limits) and has ONE Read All / Write All / Burn for the three boards: `dingoConfig/domain/CustomPdm/PdmOps.cs` (boards one after another, each waits for the board's own result; Write All and Burn refused unless A1, A2 and B are in the project, connected and read; Write All and Burn stop at the first failure, Read All goes on past a failed board, and every board keeps its result line; Burn only from its own button, after a fresh config check of all three) and `dingoConfig/application/Services/PdmOpsService.cs`. Stock edits for it: `DeviceManager.CheckConfig` public, one service line in `web/Program.cs`.
- Route B phase B3: `/pdm` "PDM settings" panel (`dingoConfig/web/Components/CustomPdm/PdmSettingsPanel.razor`, logic `dingoConfig/domain/CustomPdm/PdmLinked.cs`): temperature warn / critical / recovery / critical-soon margin set once for A1, A2, B (shows when the boards differ); fan on / off set once, written into the 6 A2 params that hold them (conditions 27-28, CAN inputs 25-28 operands; off below on, 0-125 C; left alone if A2's fan logic was changed by hand); base IDs with checks (range, no block overlap, A1 below A2) and Move = the stock Modify message (board moves at once, A2's fan CAN inputs follow A1 / B; then Write All and Burn). "New PDM" button on `/pdm` when no board is in the project (the menu entry PDM is always shown): A1, A2, B with our firmware's factory defaults (`dingoConfig/domain/CustomPdm/PdmFactoryDefaults.cs`, `PdmNewProject.razor`; proven equal to fresh boards param by param in the sim tests), so its Write All needs no Read All first (it replaces what the boards hold). Stock edits: `FwDevice.MaxCyclicId` follows a BaseId change (a device moved to a higher ID heard nothing), NavMenu entry always shown.
- Route B phase B5: DBC files for the ECU from ONE generator, `dingoConfig/domain/CustomPdm/DbcExport.cs` (source: the cyclic signals the app decodes, checked against `firmware/boards/custompdm_*/msg.cpp`). `dotnet run --project ui\tools\DbcGen` writes `firmware/dbc/custompdm_A1_0x500.dbc`, `_A2_0x540`, `_B_0x580` and `custompdm_PDM.dbc` (all three; `-- --check` compares only); the /pdm "Export DBC" button downloads one file with the boards of the project at their own base IDs (`web/Components/CustomPdm/DbcExportButton.razor`, `web/wwwroot/js/custompdm/download.js`). Signal names carry the board (`A1_Output1_Current`); msg 3 byte 7 is three flag bits; keypad msgs 24-26 are left out (the app does not decode them). A test keeps the committed files equal to the generator.
- Route B phase B4 (w1 recipe, DECISIONS 2026-11-16, proven in `firmware/sim` s1 S7): /pdm "Links" panel (`dingoConfig/web/Components/CustomPdm/PdmLinksPanel.razor`, logic `dingoConfig/domain/CustomPdm/PdmLinks.cs`): any of the 24 digital inputs as the trigger of any output; per output: source input, loss mode, condition. Same board: the output uses the input directly. Other board: nothing is set on the input board P; on the output board Q one stock CAN input L listens to one bit of P's msg 37 (base + 0x27, every 100 ms), Equal 1. Loss mode per output (u3c / w1, default off): off = L (time-out 1 s), hold = L without time-out (off at power-up), on = virtual input `LOST OR L`, condition = `(LOST AND C) OR L` (C = an input / condition of Q, picked in the panel). Shared per source board on Q while it has on / condition links: ALIVE (CAN input on P's msg 37, bit 0, `>= 0`, time-out on), SEEN (same, time-out off) and LOST = `SEEN AND NOT ALIVE`, made with the first such link and freed with the last; LOST always gets a lower virtual-input index than every link virtual input (else a 2 ms drop at the time-out). No critical start-up exception (DECISIONS 2026-11-16): every linked output stays off until boot is done and P's first frame has arrived; a board read back with the dropped critical recipe (`NOT ALIVE` in place of LOST) shows "old recipe" and Upgrade converts it (mode and condition kept). Cost on Q: per source board 2 CAN inputs + 1 virtual input; per link 1 CAN input (+ 1 virtual input for on / condition). Ownership: a CAN input / virtual input is ours only when every field matches one of these patterns (ID = another board's msg 37); old B4 "on" links (slot Equal 0 + `NOT slot OR false`, on at power-up until the first frame) are shown as "old recipe" and converted only by the Upgrade button (one confirm); anything else is the user's and never changed. Free = disabled with ID 0 (virtual input: disabled, no variables), never A2's fan CAN inputs 25-28, fan virtual inputs 12-14 or the load-shed ones 15-16; the lowest free one is used; a refused edit changes nothing. An output whose trigger is set by something else asks "already assigned. Overwrite?" (g1). Links live only in the boards' params, so Read All / an app restart shows them again; base-ID Move takes link and ALIVE / SEEN slots along. Refused: the fan output (A2 OUT2), a paired output. Measured on the sim through the /pdm Write All + Burn and a power cycle (`PdmW1LiveSimTests`, 0.5 ms steps): linked outputs 0 ms ON before P's first frame (P silent 1.5 s, key on with both boards, key on with P's input OFF), on 3 ms after it; at loss one clean change 1005 ms after the last frame, no blip on outputs whose mode keeps their state. Input -> output pin 47-125 ms across boards, 25 ms on the same board (B4). Sim bridge: `PIN <board> <o>` reads an output pin, `RESTART <board> ...` power-cycles boards (FRAM kept), `TRACE` records pin changes.
- Read on connect (p2a): when a board (type 14 / 15) connects, /pdm reads it by itself (a Read All of just the boards that connected, one after another, through `PdmOps`); while a Read All / Write All / Burn runs, it waits and goes after the run. If the PC holds unsaved edits for that board, /pdm asks instead: "Keep PC settings" (nothing read, Write All later) or "Take the board's" (Read All of that board). Nothing is written or burned by it. "Unsaved edits" = the board's PC param values differ from a snapshot of them taken on the stock "Read Successful" / "Write Successful" of that device in this session (from /pdm or the board's own page; the board card shows "PC changes not written"). No snapshot yet: a New PDM board counts as edited until written; a hand-added or loaded device does not (it cannot be written before a Read All anyway). The config CRC check is not used for it: a mismatch cannot tell a PC edit from a board changed elsewhere. The check is made again every 100 ms, so a board that waits and gets edits is asked about, and an asked board whose edits are gone (written, or undone) is read. Connect = offline to connected as seen by the `PdmOpsService` timer (on from the first /pdm visit; the first look counts as a connect). Logic `dingoConfig/domain/CustomPdm/PdmAutoRead.cs`; switched on in `web/Program.cs`.
- CAN dummy pack (Dan, 2026-11-16: d2b, L1a, L2, L3a, L4a): the DBC files (and the Export DBC button) also give every output / input signal its PDM-wide name (`PDM_Out17_Current`, `PDM_In15_State`, numbered as `/pdm` via `PdmView.OutputNumber` / `DigitalInputNumber` / `AnalogInputNumber`) as the string attribute `PdmName` plus the start of its comment; the signal names stay per board (one DBC message cannot hold two signals with one name). `ui/tools/CarCanDummy` (run by the same `dotnet run --project ui\tools\DbcGen`, `-- --check` too) writes DUMMY TEST COPIES into `docs/car-can-dummy/`: `link_pdm_receive.dummy.json` / `.lcs` (Link receive channels in st185's JSON encode / .lcs decode forms) and `bus-load.dummy.md` (from the hand-made `can-id-table.dummy.md`, which it also clash-checks); `ecu-pdm-control-plan.dummy.md` is a hand-written plan. Never a source of truth: the st185 repo is read only. Tests: `CarCanDummyTests` (st185 `bench/check_parity.py` rules re-implemented, not run).
- One-PDM editor phase 1 (DECISIONS 2026-11-16 "ONE PDM", g1, p1 / p3): (1) Conflict engine `dingoConfig/domain/CustomPdm/PdmEngine.cs`: one model of every function of A1 / A2 / B (inputs, CAN inputs / outputs, virtual inputs, conditions, timers, counters, flashers, math blocks, outputs incl. PWM duty input, keypads, wiper, starter, device block), what each one reads, and who owns each allocatable one: reserved (A2 fan logic: CAN inputs 25-28, conditions 27-28, virtual inputs 12-14; load-shed example on every board: conditions 29-32, virtual inputs 15-16), links / shared ALIVE / SEEN / LOST (B4 w1), a /pdm trigger (one output), set by hand, or free (fresh-board values and nothing reads it). Problems it reports: output driven twice (paired output with its own trigger), resource used by two owners, reference to a disabled / missing resource (also an other-board input that is off), link slot changed by hand, reserved slot touched. (2) Output triggers on /pdm (`PdmTriggers.cs`, `web/Components/CustomPdm/PdmTriggersPanel.razor`): the 24 outputs in one list, each trigger in words (e.g. "IN15 AND IN9, on-delay 2 s"), and an editor per output: one input, AND / OR / NOR of 2-3 signals with NOT per signal, a value above / below a level with hysteresis (battery voltage, board temperature, analog input mV, hand-made CAN input values, math, counters), then an optional timer (on-delay, off-delay, pulse) and flasher. Cost on the output's board: input 0 (NOT: 1 virtual input); AND / OR / NOR 1 virtual input; level 2 conditions + 1 virtual input; timer +1 timer; flasher +1 flasher; each input of another board +1 CAN input (the links 'off' recipe: off 1 s after that board's msg 37 stops; nothing set on the input board). Triggers are read back from the params (no PC-only state): they survive Read All and an app restart. Replacing a trigger that is not the editor's own (a link, something hand-made, or parts shared with another output) asks "already assigned. Overwrite?"; hand-made functions are then only unhooked, never changed; the editor's own parts go back to fresh-board values. A full board is refused with what is in use (nothing changed). Per-board use (used / free) is shown above the list. Links (B4) stay as they were; their "Remove unused" never touches a trigger's CAN input; the Links panel overwriting a trigger frees its parts. (3) Advanced (per board) `/pdm/advanced` (`PdmAdvanced.razor`, button on /pdm): the stock Configuration and keypad tabs of one board; the board's own device page shows only its Dashboard (stock edit: `FwDeviceTabs.razor`). Every edit there is checked by `PdmEngine.CheckEdit` (150 ms poll of the PC values): changing a claimed function or replacing an output's trigger asks "X is already assigned to Y. Overwrite?" with any new problems listed (Cancel puts every value back); critical settings are refused there. (4) Critical settings lock (`PdmCritical.cs`, `PdmCriticalDialog.razor`, PDM settings panel): base IDs, CAN bit rate, critical temperature and the outputs kept on at critical temperature are read-only on /pdm and change only with Unlock + type the new value twice + Change (base ID: then the B3 Move); the Devices page Modify keeps a custom-pdm board's base ID read-only (stock edit: `Devices.razor`). Proof: `PdmEngineTests`, `PdmTriggersTests`, `PdmTriggersLiveSimTests` (AND / NOT / OR / NOR, level with hysteresis on the analog input, on-delay, flasher and other-board signals on the sim boards through Write All, then read back by a fresh PC).
- Tests: `tests/CustomPdm.Tests` (C#). The live ones talk to the host simulation of our firmware through `tests/sim_bridge.py`.

## Run on DansPC (PowerShell, repo root)
Build and start the app (then open the address it prints):

    dotnet build ui\dingoConfig\dingoConfig.sln
    dotnet run --project ui\dingoConfig\web\web.csproj

Build the firmware host sim once (WSL), from a committed branch:

    wsl -e bash -c 'S=~/scratch/ui-sim; rm -rf $S; mkdir -p $S/src $S/so; cd /mnt/c/projects/active/custom-pdm; git archive main firmware | tar -x -C $S/src; cd $S/src/firmware; for u in 1 2; do bash sim/build.sh custompdm_a $S/so $u; done; bash sim/build.sh custompdm_b $S/so 1'

Tests (without `CUSTOMPDM_SIM_SO` the live ones are reported as Skipped):

    dotnet test ui\tests\CustomPdm.Tests
    $env:CUSTOMPDM_SIM_SO='/home/daniel/scratch/ui-sim/so'; dotnet test ui\tests\CustomPdm.Tests

Use the app with the simulated boards (A1 0x500, A2 0x540, B 0x580, 1000K): start the bridge, then in dingoConfig pick adapter "SLCAN TCP", port `localhost:3333`, bit rate 1000K, add the three devices (types "custom-pdm A" / "custom-pdm B"), and open /pdm: it reads the connected boards by itself (read on connect, p2a) before any write (a hand-added device holds stock dingoPDM defaults, not our factory defaults). The real-time sim is slower than a board: one Write All takes 40 to 55 s per board through the bridge (about 39 s on 2026-11-16). The /pdm Write All has no fixed wait: per board, it restarts on every frame the PC sends to that board and every config reply from it, fails "no reply (no answer for 10 s while writing)" 10 s after the last one, and gives up at 5 min per board ("write not confirmed in 5 min"):

    wsl -e python3 /mnt/c/projects/active/custom-pdm/ui/tests/sim_bridge.py /home/daniel/scratch/ui-sim/so --slcan-tcp 3333
